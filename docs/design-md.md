# DESIGN.md

`DESIGN.md` at the repository root is a machine-readable description of the Modeless token layer, following the [DESIGN.md format](https://github.com/google/design.md) (format version `alpha`). It exists so agents and external tools can read the design system's colors, typography, and shape language without parsing TypeScript or CSS.

## Generation

`DESIGN.md` is generated by `scripts/generate-design-md.mjs` and regenerated on every `npm run build`. **It is committed to the repository** so that it can be read directly from GitHub and shipped in the package tarball, and regenerated in CI so a stale file cannot survive a build.

```bash
npm run design:generate   # rewrite DESIGN.md from source
npm run design:lint       # validate structure (runs in the release gate)
```

Do not edit `DESIGN.md` by hand. Edit `src/styles/modeless-theme.css` and regenerate.

## Where the values come from

The generator reads `src/styles/modeless-theme.css`, not `src/tokens/colors.ts`.

That follows `docs/tokens.md`, which states that CSS variables are the source of truth for theming: the theme is what actually renders. The theme aliases semantic roles onto core colors (`--primary: var(--acid-lime)`), so the generator resolves those chains to literal values, since DESIGN.md tokens cannot hold indirections.

Corner radii are a second resolution step. `tailwind.config.ts` expresses them as `calc(var(--radius) - 2px)`; DESIGN.md dimensions cannot hold `calc()`, so the arithmetic is resolved to concrete pixels (`sharp: 0px`, `panel: 4px`, `artifact: 6px`, `soft: 10px`).

## What is intentionally omitted

Two sections are declared in the front matter's `omitted` list, which suppresses the linter's missing-section warnings and records why:

- **`spacing`** — Modeless has no spacing scale. Layout uses the consuming app's spacing utilities.
- **`components`** — component styling lives as Tailwind utilities and CVA variants in source rather than as component tokens.

Motion has no home in the DESIGN.md schema at all. It is documented as a `## Motion` prose section, which the spec preserves as unknown content, but the motion tokens themselves remain in `src/tokens/motion.ts`.

## Relationship to tailwind.config.ts

**`DESIGN.md` does not replace `tailwind.config.ts`, and the exported Tailwind theme is not intended to be dropped in.** This was a deliberate decision, and the reasoning matters because the phase plan asked whether the hand-maintained config should be replaced by generated output.

The two artifacts are structurally different in kind:

| | `tailwind.config.ts` | `designmd export --format json-tailwind` |
| --- | --- | --- |
| Color values | `hsl(var(--primary))` indirections | literal hex (`#c6ff29`) |
| Structure | nested `DEFAULT`/`foreground` pairs, `product.*` group | flat, single-level |
| Font families | three stacks with full fallback chains | one family name per typography level |
| Runtime theming | works — variables can be re-pointed per scope | none — values are frozen at export |

Replacing the config with the export would break `.modeless-theme` scoping and any future light/dark re-pointing, every `-foreground` utility, every `product-*` utility, and the `font-display` / `font-ui` / `font-mono` families along with their fallback stacks.

So these are not two divergent sources of truth. There is one source — the theme CSS — with two derived artifacts serving different consumers: `tailwind.config.ts` is the **runtime implementation**, and `DESIGN.md` is the **published description**. The exports under `dist/design/` exist for external tools that want tokens in a standard format, not for this repo's own build.

The one value that did agree across both paths is the radius scale, which resolves identically.

## Known drift: colors.ts and the theme disagree

Generating DESIGN.md surfaced a pre-existing inconsistency that is **not fixed here**.

`src/tokens/colors.ts` and `src/styles/modeless-theme.css` define the same core palette twice — once as hex, once as HSL — and **11 of the 13 core colors disagree**:

| Token | `colors.ts` | theme CSS, as hex |
| --- | --- | --- |
| `panel-black` | `#101010` | `#0f0f0f` |
| `steel` | `#444649` | `#45474a` |
| `concrete` | `#8B8B8B` | `#8c8c8c` |
| `bone` | `#EEE6D0` | `#efe5cd` |
| `xerox-white` | `#F7F2E8` | `#f8f2e8` |
| `acid-lime` | `#C7FF2A` | `#c6ff29` |
| `completion-green` | `#39D98A` | `#3bd88c` |
| `electric-purple` | `#8E2EFF` | `#892eff` |
| `radar-blue` | `#2D78FF` | `#2e74ff` |
| `warning-orange` | `#FF5A1F` | `#ff571f` |
| `signal-pink` | `#FF3FA4` | `#ff3dab` |

Only `off-black` and `graphite` match.

Most deltas are one or two steps per channel and read as HSL rounding, but `radar-blue` differs by four steps in the green channel. What renders is always the CSS; `modelessColors` is what consumers get when they import a value to use outside CSS, so the two can disagree on screen within the same product.

This is left alone deliberately: `modelessColors` is public API, and changing its values is a visual change that belongs in its own reviewed commit, not a side effect of adding a documentation format. `DESIGN.md` reports what renders.

The fix, when someone takes it: make one representation generated from the other. Deriving `colors.ts` from the theme CSS matches the stated source-of-truth direction.
