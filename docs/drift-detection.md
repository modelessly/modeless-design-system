# Drift Detection

`npm run drift:check` fails when a committed generated artifact no longer matches what the current source produces.

**It reports drift. It does not correct it.** That boundary is deliberate — see [Deliberately not automated](#deliberately-not-automated).

## What it checks

| Artifact | Generated by |
| --- | --- |
| `registry/registry.json` | `scripts/generate-component-registry.mjs` |
| `DESIGN.md` | `scripts/generate-design-md.mjs` |

Both are committed *and* regenerated on every `npm run build`. Committing them makes them readable from GitHub and shippable; regenerating them means the committed copy can fall behind the code it describes.

## Why the other checks cannot see this

`registry:check` and `design:lint` run *after* `build` in the release gate, so they validate the **freshly generated** files — which are correct by construction. A stale committed copy passes every one of them while describing a component that has since changed.

That is the gap: change a component's props, commit without rebuilding, and the registry keeps advertising the old API. Every check stays green. An agent reading the registry gets a confidently wrong answer, which is worse than no answer.

## How it compares

The committed version of each artifact (`git show HEAD:<path>`) is compared against the file on disk after a build. JSON is normalised before comparison; Markdown is compared directly.

### The one excluded field

`provenance.lastModified` is the date of the last commit touching a source file, which makes it **the one field that can never be self-consistent**. A commit that changes a component also changes that component's date, so the registry committed *in* that change always records the previous one. The value only becomes correct after a second commit.

Left in the comparison, it would fail every pull request that touches a component — noise, not drift. It is still generated and still useful; it is only excluded from this equality check.

This is not theoretical. Immediately after the QA fixes landed, `registry/registry.json` showed 31 changed lines in the working tree, every one of them a `lastModified` date. A naive `git diff --exit-code` would have failed there and taught everyone to ignore the check.

## Verified behaviour

Confirmed to fail on each of these, and to pass on a clean tree:

| Scenario | Detected as |
| --- | --- |
| A registry entry hand-edited so a prop type no longer matches its component | `registry/registry.json` differs |
| A component gains a prop and is committed without rebuilding | `registry/registry.json` differs |
| A `DESIGN.md` token value hand-edited | `DESIGN.md` differs |
| A theme variable added without rebuilding | `DESIGN.md` differs |
| A generated artifact deleted or never committed | missing / not committed |

The failure prints the first differing lines, so it says what moved rather than only that something did.

## Fixing a reported drift

```bash
npm run build
git add registry/registry.json DESIGN.md
```

Commit the regenerated files **alongside** the change that moved them. That is the whole discipline this check enforces: generated output travels with its source.

## Deliberately not automated

This check does not open pull requests, does not commit regenerated output, and does not auto-merge anything.

Detection needs a track record before correction is worth automating. An automated corrector that is wrong is far more expensive than a check that is noisy, because it writes its mistake into the repository under the appearance of routine maintenance.

### Future work — do not build yet

- **Automated drift-correction PRs.** Revisit once this check has run across a meaningful number of changes without false positives. The bar to clear first: how many times did it fire, and was it right every time?
- **Auto-merge for those PRs.** Strictly after the above, and not before the trust-tier work has a track record of its own.
- **Widening coverage.** The check currently covers two artifacts. `dist/` is deliberately excluded because it is not committed.

Anyone tempted to build these should read the phased trust-tier approach in `docs/agentic-upgrade-audit.md` first: the same argument applies. A layer earns automation by being observably right, not by being plausible.
